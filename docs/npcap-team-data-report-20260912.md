# Npcap 队友 DPS / 技能详情调查报告（2026-09-12）

结论：Npcap 已能解码下发的全队累计伤害及结算技能表，但尚未证明关闭旧 Hook 请求器后，服务器仍会持续自然下发这些数据。不能把旧实验的成功表述为“纯 Npcap 已完整替代正式采集”。本报告不改变正式客户端的数据来源或战斗逻辑。

## 本次复核的证据

使用 `.codex-tmp/audit_npcap_samples_20260912.py` 重新计数已有原始解码样本，未进行游戏操作或新增主动请求。

| 样本 | JSON 行数（含辅助记录） | 团队 Common | 主动施法广播 | 结算 |
| --- | ---: | ---: | ---: | ---: |
| `gmzzdps-npcap/.codex-tmp/validation/war_dragon_auto_merged_rpc.jsonl` | 1027 | 50 | 34 | 1 |
| `.codex-tmp/npcap-party-live-1635.jsonl` | 1049 | 0 | 111 | 0 |
| `.codex-tmp/npcap-party-damage-1532.jsonl` | 289 | 0 | 31 | 0 |

后两个样本分别只有约 26.5 秒、30.7 秒，不能代表完整战斗。此前报告的 1048/287 是具名消息计数，与本次包含辅助记录的总行数口径不同。

战争巨龙样本另有 38 条 DamageSync、110 条 BeatenSync；这些消息数量不能证明全队逐击覆盖。结算包含六名成员，既有还原文件中的团队总伤为 9,148,922。

最关键的限制在 `.codex-tmp/npcap_battle_detail.json` 的 `source_policy.team_stats_origin_caveat`：当时正式 DPS 同时运行，提供了主动 TeamStats 请求器。Npcap 进程自身不发包，并不等于实验环境没有请求器。旧工程 README 中“自然收到”的描述不能作为独立可行性的证明。

## 各项能力与缺口

| 需求 | 已确认来源 | 尚未满足的条件 |
| --- | --- | --- |
| 队友 DPS | Common/Dirty 的逐人累计伤害，加统一战斗时长 | 无旧请求器时持续到达未证实 |
| 技能伤害分布/次数 | 阶段或结算的技能金额及次数表 | 团灭、退出、缺失结算时无法保证完整 |
| 暴击率 | 已验证结算字段 25 / 27 | 不能承诺战斗中连续刷新 |
| 穿刺率 | 已验证结算字段 (27 - 14) / 27 | 需计数合法且分母大于零，不等于逐技能穿刺率 |
| 技能时间轴 | 实际收到的 CastSkill 广播 | 不覆盖所有被动、DOT、逐跳伤害，不包含可靠单次金额 |

不能用施法动作、职业模板、Boss 掉血或动画推算缺失伤害，也不能把无法获取的字段填零来宣称完整。

## 仅沿 Npcap 继续验证的路线

1. 正式 Hook 客户端正常退出后，单独运行 Npcap 探针。完整记录入队、开战、胜利、团灭重开、退出五种场景，保留抓包丢包/乱序/解码失败指标。
2. 由用户在游戏原生界面中手动打开与关闭队伍战斗统计，观察它是否自然产生 Common/Dirty/个人详情请求及回复。原有字符串中发现过 DungeonBattleStatistics 和 ReqCommonCombatStatisticsByTeam，但名称本身不能证明触发条件。
3. 对比每名队友稳定身份、累计值、技能表和时间轴覆盖，明确数据源、开始与结束时间；不把同时运行 Hook 的对照实验当成纯被动覆盖证据。
4. 继续分析未知数字 RPC 与属性同步，要求其数值、角色归属和累计趋势能逐一匹配实战，才可接入统计。尚未找到可靠的新队友伤害字段。

现有探针仍使用只读解码状态引导，不等于已经实现完全不访问进程的解密方案；关闭实体资料内存读取也不等于移除了全部解码引导。若最终要求连密钥/压缩状态也完全来自网络，还需要单独验证会话初始化能否仅凭封包恢复。

## 发布边界与下一步

v0.2.3d 正式包继续使用当前 Hook 链路，不混入未验证的 Npcap 替代方案。用户当前正在测试正式链路，不为调查中断本次测试。

下一项有意义的实测需要单独安排“关闭正式客户端、只运行 Npcap”的完整战斗。服务器若没有向该客户端下发某项数据，单纯改善捕获、重组或解析无法补出它。目前不能承诺每一场队友 DPS、技能分布、暴击和穿刺都稳定完整。
