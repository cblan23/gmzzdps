# 公网下载速度异常核查材料

实例：i-uf66kz57l6crwbgfde58，cn-shanghai，公网 IP 47.116.62.116。
用户控制台显示峰值公网带宽 200 Mbps。请核查这个值对应的实际网络计费/共享/峰值约束和当前生效配置，不能仅以客户端测到低速判定已占满。

现象：2026-09-11 21:04 左右 TCP/TLS 严重重传、连接不可达；2026-09-12 多名用户更新下载极慢。本机在 12:15～12:24 的有限对照稳定约 83～85 KB/s。测试时停止了其他自发整包下载；生产业务仍运行。

实测：

| 方式 | 结果 |
| --- | --- |
| 绕过本机代理的 HTTPS 静态文件、1 MiB | 12.264 秒，85,500 B/s |
| HTTP 80 同文件、1 MiB | 12.579 秒，83,357 B/s |
| HTTPS 443 同文件、1 MiB | 12.312 秒，85,166 B/s |
| 只针对诊断 IP 临时 MTU 1200、1 MiB | 12.599 秒，83,227 B/s |
| 原 Python 代理更新接口 | 同样低速，接收字节与文件一致 |

临时 BBR、关闭 TSO/GSO 对照未见足以恢复下载的改善，均已恢复 CUBIC、TSO/GSO 开启；单 IP MTU 路由已删除，临时 HTTP 诊断入口已删除。没有通过关闭校验或重启整机掩盖问题。

慢连接示例：12:19 前后，服务端累计发出约 8.98 MB，重传约 2.14 MB，cwnd=4，应用还有约267 KB待发送；RTT约22ms。重传字节是该连接累计值，不等同于链路丢包率。

主机检查：网卡驱动 errors/drops 为零；fq_codel 本地丢弃/overlimits/backlog 为零；无主机 443 限速规则；conntrack 1166/65536未满；CPU/内存未耗尽。数据库慢事务已另行修复，不足以解释同一静态文件的公网低速。

历史对照：9月11日21:20、21:30十分钟区间整机eth0出网仍约1314/1443 KiB/s。这是整机区间均值，不是单用户下载能力，也不能断言昨晚21:04之后始终被限制为85KB/s。
