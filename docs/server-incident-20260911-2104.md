# 2026-09-11 21:04 附近访问异常排查

更新：已从阿里云主机监控代理缓存恢复约 15 秒粒度的故障时段指标，确认 TCP 重传骤增先于数据库 503。下文保留初查过程，最终证据见末节。

用户反馈服务器无法访问，随后表示已恢复并要求查原因。本轮只读诊断，没有重启/部署服务、修改数据库或网络设置。

## 确认的现象

- 后台服务 MainPID 3358339 自 18:31:00 持续运行，NRestarts=0。Nginx 同样没有重启。
- 首次检查服务器内网 health 返回 ok，Nginx 本机 `/dps-monitor` 在 0.009 秒返回预期的未认证 401。
- 同时从用户电脑访问公网先后发生 12 秒连接超时；另一次 IPv4 请求 DNS 0.018 秒、TCP 建连 0.040 秒，但 TLS 完成到 7.354 秒。还有一次 DNS 正常后 TCP 连接仍超时。
- 恢复后同一公网 health DNS 0.012 秒、TCP 0.034 秒、TLS 0.068 秒、整体 0.098 秒。
- 访问日志 21:02/21:03 每分钟完成约 5,146/5,279 次请求；21:04 降至 1,666，21:05～21:09 每分钟约 1,000～1,200。会话开始/结束及重新查询更新增多，符合断联后重连现象。
- 21:09 有 92 次 HTTP 503，21:11 有 33 次，共 125 次。
- 服务日志明确出现 `SQLite busy response: database write queue is busy`。这不是仅凭 503 猜测 SQL 错误。

## 数据库队列的明确机制

生产 `dps_monitor_server.py` 使用 `_DATABASE_WRITE_LOCK = threading.RLock()` 串行化写事务。
`_database_write_guard()` 最多等待 `SQLITE_WRITE_QUEUE_TIMEOUT_SECONDS = 5.0` 秒，超过即抛出 `database write queue is busy`，转换为 HTTP 503/server_busy。
登录、心跳、战斗时钟等多个接口共用这一写入队列，拥堵会同时影响这些接口。没有足够记录确定当时哪一笔事务最先持锁过久；不能把队列超时等同于已找出所有锁冲突来源。

## 系统与网络证据

- 排查时可用内存约 915MB，根分区 72%，剩余约 11GB；未看到此时段内核警告或 OOM。
- sar 20:50～21:00 平均 CPU idle 30.40%，21:00～21:10 idle 50.53%；对应可用内存约 996MB/986MB。十分钟统计不能排除瞬时峰值，但不支持持续 CPU/内存耗尽的结论。
- 同期 sar eth0 平均发送 1513/849 KiB/s，驱动错误/丢包计数为 0。驱动零丢包不代表公网链路无丢包。
- 异常期 ss 显示 1531 个 orphaned TCP、多个 HTTPS 连接有约 3.8KB 待发送；恢复后 orphaned 降为 16。与连接握手/关闭积压一致，但不能单独定位到云带宽配额。
- 恢复后 3 秒样本出站约 1.765 Mbps，TCP retrans 7 / out 2557。
- Nginx 配置 worker_connections=768，未查到限速项，也未见同期 worker_connections 不足或新增上游拒绝错误。
- 有更新包下载，但访问日志记录的是请求完成时的累计字节数，不能直接当作该分钟实际瞬时带宽。

## 结论边界

已确认公网 TCP/TLS 可达性异常，随后/同时出现后台数据库写入队列超时；后台进程没有崩溃。公网问题比 503 波峰更早出现，不能全部归因于数据库。
可能存在断联重连放大写入压力，但尚不能断定初始公网异常一定由更新下载、带宽耗尽或云网络故障造成。
要最终确定公网侧触发因素，需要阿里云 ECS 21:00～21:15 的公网流入/流出、带宽限制及丢包/连接监控。当前本机十分钟 sar 与访问日志不足以代替这些数据。

`avg_RetransRate` 是代理报告的 TCP 重传率指标，不是逐包丢失概率。该指标峰值可超过 100%，不可表述成“97%用户数据包丢失”。21:05 附近报告平均重传约 674 段/秒，对应 avg_OutSegs 约 696 段/秒。

故障期间 Nginx 两个 worker 的打开文件数未接近 768 连接上限，例如 21:06:15 为 48/47、21:09:30 为 85/88。应用与代理进程无重启；INPUT 防火墙为空且策略 ACCEPT；配置文件没有当天 21:04 的变更。

确定结论：最初故障表现为服务器公网 TCP/TLS 传输阶段严重重传/连接不可达，应用收到的业务请求骤减，CPU随之下降；数据库写入队列的 503 波峰较晚，不能解释 21:04 的初始断联。

21:09:45、21:11 附近还出现显著 I/O 等待，与写入队列超时重合。排查期间的 journalctl 大范围日志读取也与部分 I/O 波峰重合，可能放大该阶段压力；不将其未经验证归因成“重连必然导致所有 503”，后续已改为小范围离线指标分析。这些读取在最初公网故障之后发生。

仍需云侧核实的触发因素：公网带宽/流量管理限额、云网络路径或防护策略事件。主机代理指标说明发生了严重重传，但不能确定在哪个网络节点丢弃或延迟。

## 继续收窄（用户要求对症修复）

- 实例元数据返回规格 `ecs.e-c1m1.large`，属于经济型共享实例，2 vCPU / 2 GiB。官方规格表列出网络基础/突发 0.2/最高2 Gbit/s，但这不是实际购买的公网带宽值，也不能据此认定该次触发网络限额。
- 官方对未明确标注连接数的规格不提供连接数保障；仍需云侧事件或配置证据，不能将“共享型”直接等同于本次故障原因。
- 服务日志限定 21:03～21:05 查询 `/update/download` 无记录（请求响应头开始写出时会记录日志）。没有证据将故障触发点归于该时段新启动的更新下载，不能直接拿迁移 CDN 当作已确认根因修复。
- `licensing.py` 的 GET 和 POST 使用 `urllib.request.urlopen`；当前 Python 标准库 `AbstractHTTPHandler.do_open` 每次创建 HTTPConnection，明确设置 `Connection: close`。心跳/战斗计时等高频调用不能复用连接。
- `_request` 网络异常后固定等待 0.2 秒重试一次。大量客户端同时遇到网络异常时有集中重试风险，这是明确的放大因素，不等于已证明它触发了 21:04 的初始网络异常。
- 可审查的应用改进方向是连接复用、带抖动的有界退避、缩短写事务；本轮只诊断，未实现或部署这些改动，也不承诺这些改动能消除云网络故障。
