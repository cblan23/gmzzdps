# 0.0.15 数据能力实证与可行性报告

本报告只采用客户端配置、解码后的真实网络记录和同一日志的双版本回放结果。没有按比例补齐、按血量估算、按职业猜技能，也没有把未知伤害强行分给 Boss。

## 结论

| 项目 | 结论 | 0.0.15 处理 |
| --- | --- | --- |
| 队友技能分布 | 可修复 | 采用阶段/结算表字段 `34` 的逐技能绝对伤害及字段 `33` 的次数；只在该玩家字段 `6` 总伤与实时团队总伤完全一致时生效 |
| Boss 战逐怪伤害 | 只能精确恢复本机已收到的部分 | 展示带“玩家 ID + 怪物 ID + 伤害”的精确包；其余团队总伤统一显示为“未分配目标”，不猜归属 |
| HPS 与治疗分析 | 可实现，覆盖度必须分级 | 服务器字段 `17/35`提供完整有效治疗及技能分布，`OnMsgHealSyncV2` 提供总治疗、过量、目标、峰值和响应样本 |
| Boss 属性 | 可建立完整配置目录 | 当前生产清单共 70 个模板，保留原始配置值，不把动态等级 `-1/-2` 改成推测等级 |
| Boss 战斗技能 | 现有日志内可实证 19 个模板 | 只接受攻击者实体已绑定确认 Boss 模板的精确伤害包；无伤害机制与未打过的 Boss 标为“未观察到” |

## 队友技能分布

服务器阶段/结算行已经直接给出：字段 `6` 为玩家总伤，字段 `33` 为逐技能次数，字段 `34` 为逐技能绝对伤害。真实 6 人结算样本中，5 名远端队友的技能表通过了“结算总伤等于实时团队总伤”的严格门禁；技能合计不足的唯一差额 `2,504` 被保留为“未归类伤害”。

采用规则如下：

1. 实时总伤继续只来自现有 Common/Dirty 团队累计值，结算表不改写总伤。
2. 只有同一玩家的字段 `6` 与当前总伤完全相等，才采用字段 `34/33`。
3. 技能和小于玩家总伤时，只加入精确差额“未归类伤害”。
4. 技能和大于总伤、玩家不匹配或结算场次不匹配时，整份技能表拒绝使用。
5. 不缩放技能金额，不根据职业或本机玩家比例补齐队友技能。

真实回放还发现一场较早的双人战斗可新增 1 名队友的服务器技能分布；最终 6 人战斗保持 5 名远端队友使用服务器技能表，本机玩家继续使用精确回调。

## 逐怪伤害

现有团队结算没有提供“玩家 ID + 怪物 ID + 伤害”三元组。对 62 份生产日志的精确方法名检索中，以下候选响应均为 0：

```text
RetDungeonBattleStatistics
RetMonsterBattleStatistics
RetNpcCombatStatisticsByTeam
RetDirtyNpcCombatStatisticsByTeam
OnMsgUpdateDungeonBattleStatistics
OnMsgUpdateDungeonTeamPlayerBattleStatistics
```

真实结算字段反证：字段 `36` 在 6 名玩家上分别与字段 `7` 的承受伤害完全相等；字段 `37` 只出现 1 个关系计数，没有伤害金额。因此二者都不能作为玩家对各怪物的伤害分布。

同一场 6 人 Boss 战的直接结果是：

| 项目 | 数值 |
| --- | ---: |
| 服务器精确团队总伤 | 6,276,202 |
| 带目标 ID 的本机精确伤害 | 7,444 |
| 可分配到具体怪物 | 7,444 |
| 缺少目标维度的团队伤害 | 6,268,758 |

所以 0.0.15 的可行做法是保留 `7,444` 的真实逐怪归属，并把 `6,268,758` 明示为“未分配目标”。把它全部归给主 Boss、按血量变化分摊或按本机占比外推，都会产生无法证明的错误数据，本版本不采用。

## HPS 方案

### 直接数据源

真实协议已确认：

```text
OnMsgHealSyncV2 = [治疗者ID, 目标ID, 技能ID, 总治疗量, 有效治疗量]
结算字段 17 = 玩家有效治疗
结算字段 35 = 按技能有效治疗
```

匿名样本中捕获 838 条可解析治疗事件：总治疗 `617,198`、有效治疗 `27,722`、过量治疗 `589,476`，没有出现“有效治疗大于总治疗”的非法事件。最终结算中字段 `17` 和字段 `35` 的合计均为 `29,579`，两条独立路径完全一致。

### 指标定义

| 指标 | 精确定义 |
| --- | --- |
| HPS | 有效治疗 / 团队统一战斗秒数 |
| 总治疗量 | `OnMsgHealSyncV2` 的总治疗量之和；逐包覆盖不完整时显示 `--` |
| 有效治疗量 | 服务器字段 `17` 优先，逐包完整时与回调交叉验证 |
| 过量治疗 | 总治疗量 - 有效治疗量；总治疗覆盖不完整时显示 `--` |
| 过量率 | 过量治疗 / 总治疗量；缺少完整总治疗时显示 `--` |
| 技能治疗占比 | 服务器字段 `35` 的技能有效治疗 / 玩家有效治疗 |
| 治疗目标占比 | `OnMsgHealSyncV2` 中目标有效治疗 / 已观测有效治疗；覆盖不完整时明确标注“已观测部分” |
| 峰值 HPS | 精确逐包有效治疗的任意连续 5 秒窗口最大值；逐包不完整时显示 `--` |
| 响应时间 | 队友首次观测到掉血后，到第一次有效治疗的间隔；连续掉血在首次治疗前只形成一个样本 |

响应时间同时保存平均、最快、最慢、样本数和已覆盖目标数。血量样本只接受已经绑定到真实队伍成员、带可信最大血量的实时 HP 更新；未知指针、Boss HP 和异常数值不会进入响应统计。真实 6 人回放形成 30 个响应样本。

### 覆盖度

| 标记 | 含义 |
| --- | --- |
| `server_verified_callbacks` | 服务器有效治疗/技能与逐包明细完全一致，所有指标可展示 |
| `server_effective_with_partial_callbacks` | 有效治疗和技能完整；总治疗、过量、目标、峰值、响应只覆盖已收到部分 |
| `live_exact_callbacks_unverified` | 当前逐包均为精确事件，但尚无服务器结算验证完整性 |

主窗口、迷你窗口和历史记录均支持 DPS/HPS 切换；治疗详情包含技能治疗和治疗目标两页。服务器统一战斗时间会同时重算历史 DPS 与 HPS，只改变除数，不改变任何伤害或治疗总量。
