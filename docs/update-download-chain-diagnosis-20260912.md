# 在线更新慢、失败与重复带宽：代码及现场核查

本次仅诊断。下载入口继续按用户此前要求暂停，不恢复下载、不重新发布客户端。

## 已确认

1. 当前公网下载接口返回 503 / `update_download_paused`。最近十分钟 30 次请求均为 503，日志响应正文总共 1350 字节。因此这些新请求没有在传 81 MB 安装包，不能把当前所有带宽占用继续算作更新下载。
2. v0.2.3c 成品 81,024,512 字节，v0.2.3d 为 81,046,528 字节，仅增加 22,016 字节。不是 d 版本安装包体积突然膨胀。
3. `licensing.py` 下载总时限为 300 秒，所有尝试共享该 deadline。81,046,528 字节要在 300 秒完成，仅文件有效载荷就需平均约 2.161 Mbps。此前整机 eth0 观测为 1.5～1.7 Mbps，且含重传与其他服务流量；若持续如此，单用户也难在时限内完成，多人分摊更差。不能由此推断实际购买带宽上限。
4. 下载过程最多尝试两次，每次从 0 开始；每次失败 finally 删除 `.download`，重试前只等 0.2 秒。没有 Range/断点续传。早于总超时的断连或校验失败可导致自动重下，用户手动重试又会开始新轮次；达到总时限则停止，不是无限自动重试。
5. 下载不完整 (`written != update.size`) 与 SHA256 不符使用同一“更新文件校验失败”提示。因此该提示不能证明完整安装包损坏。此前主动断开下载也会制造不完整文件错误。
6. UI 使用后台下载线程，代码不是把整个 HTTP 下载同步放进 Tk 主线程。但显示进度按整数百分比变化才更新，约每收到 810 KB 才有新百分比；网络读取每批最多 256 KiB。低吞吐或停顿时看起来长时间不动。此设计不能解释所有真正的窗口无响应，需要相应 UI 线程日志另查。
7. 安装包由同台 ECS 的 Python 更新接口经 Nginx 向用户发送，与鉴权等业务共享公网出口。现场曾见 Nginx 有约 81 MB 的代理临时文件，说明应用可以快速把文件交给代理；外网慢不等于数据库正在阻塞文件读取。现有下载处理没有 Range 支持，也没有下载分发隔离。

## 连锁影响

低有效吞吐/多人下载 → 300 秒时限不足或中途断开 → 不完整文件/超时报错 → 已下载内容删除、自动或手动从头重试 → 重复消耗共享出口。TCP 重传还会增加传输开销；但主机指标不能定位公网丢包节点或证明云端限速。

## 待实施（本次未改）

- 稳定版本文件地址、Range/If-Range 与一致性验证配合断点续传；错误时保留可验证的部分文件。
- 用持续无进展超时管理慢速下载，避免 300 秒总时限与实际带宽冲突；限制重复重试，尊重维护响应。
- 区分维护暂停、连接中断、长度不足、完整文件哈希失败，给出准确中文提示。
- 进度按字节/时间更新，显示速度和停滞状态，支持取消。
- 后续评估将大文件分发与鉴权出口分离。未获得云侧购买带宽/监控前，不宣称升级服务器即可消除当前网络重传。
